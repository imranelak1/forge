# ADR 014: Scoped JUnit uploads and evidence-based test intelligence

Date: 2026-09-23. Status: Accepted for Phase 6 implementation.

## Decision

Accept direct, uncompressed JUnit XML through a machine-only API authenticated by a repository-scoped `test_reports:write` token. Verified organization owners/admins create and revoke these expiring credentials; a credential cannot read reports or act as a user. Require an already imported exact GitHub workflow run and attempt in the authorized repository. Copy its branch and full commit SHA rather than trusting XML identity assertions. Missing parents are rejected for retry after synchronization, not retained as unverified engineering data.

Persist an encrypted report receipt and durable job atomically, then parse outside the database transaction. Reuse the existing 60-second lease and fencing mechanism; recheck organization, repository, installation and token access before committing. The worker writes suites, identities, executions, report counters and successful supersession together. XML syntax/security errors terminate with fixed error codes; transient processing failures have bounded retries. Raw XML is encrypted pending processing, cleared on terminal processing/cancellation and subject to a one-day expiry with bounded cleanup. Normalized evidence and receipt/dedup metadata remain; no new normalized-history expiry policy is implemented here.

Use standard-library Expat callbacks rather than building an XML tree. Require Expat 2.6 or newer, keep large-token reparse protection enabled and reject DTD declarations, custom entities and external references. No file or network resolver exists. Enforce 10 MiB input, 100,000 executions including retries, depth 64, 10,000 suites, 500,000 elements and bounded attributes/identity fields. Archives and compressed uploads are unsupported. Python documents XML attack classes and Expat's relevant controls. [Python XML security](https://docs.python.org/3.13/library/xml.html), [Expat parser controls](https://docs.python.org/3.13/library/pyexpat.html)

Preserve suite occurrences, parameterized names and every explicit execution. A logical identity includes framework, file, class, name and explicit parameterization; missing file/class uses the suite path with fallback quality. Indistinguishable repeated names become separate ambiguous identities and never establish a retry. Support Surefire's documented `flakyFailure`/`flakyError` and `rerunFailure`/`rerunError` ordering, including a final successful execution for the former. Do not infer per-retry durations from an overall duration: Surefire's testcase time belongs to the final successful run or initial failed run respectively. Other retry metadata produces quality warnings rather than invented ordering. [Surefire retry reporting](https://maven.apache.org/surefire/maven-surefire-plugin/examples/rerun-failing-tests.html)

Persist failure/error/skipped messages up to 2,048 characters as untrusted tenant-scoped text; do not retain captured stdout/stderr, properties or raw XML after processing. Names and messages can still contain sensitive source-authored content. Readers require ordinary tenant authorization, UI rendering treats these strings as text, and worker logs contain fixed outcomes/codes rather than report content. Invalid, negative, nonfinite or greater-than-one-year durations become missing with a warning. Declared counters are compared with final leaf outcomes, without double-counting nested suites or retry attempts.

## Metrics and corrections

Test pass rate uses final explicit executions from non-superseded completed reports on the latest completed workflow attempt: `passed / (passed + failed + error)`. Skipped cases remain visible outside that denominator. Earlier attempts and retry executions remain inspectable. Completed parsing means the submitted XML was processed; it does not prove that every job or shard uploaded a report.

Potential-flakiness evidence groups repository, identity, branch, environment, report key and shard. The default policy requires at least 10 final outcomes in 14 days, failure fraction between 0.05 and 0.95 inclusive, and at least two pass/fail transitions. Failures include test errors. Ambiguous identities cannot be attributed historically; fallback identity or missing branch/environment reduces confidence. Policy versions, samples, transitions and window bounds accompany results. A potential flag is a reason to investigate, not proof of a flaky defect or its cause. Same-SHA workflow retry reversals are supporting evidence, not additional fabricated final executions.

An identical report identity and digest reuses its original receipt. Changed content must explicitly identify the current report it supersedes. Old evidence stops contributing only when its replacement commits successfully; failed corrections cannot erase a valid sample. Signed pagination and tenant/repository references preserve the same scope across metrics and drill-down.

## Consequences and limits

The initial integration requires GitHub Actions history to exist first and does not fetch artifacts, unzip archives, accept standalone reports or expose a browser upload proxy. Workflow completion retains Phase 5 provenance: a complete jobs history may provide a labeled last-job proxy, while unknown completion remains outside timed metrics. There is no expected-shard manifest, so absent uploads cannot support a healthy overall test claim.

The optional local demo generates actual JUnit documents and uses the parser plus production persistence helper. Fourteen synthetic observations per repository share a stable branch/environment, making the configured sample and transition rules observable. Corrections, nested suites, ambiguous names, parameters, skipped/error cases, explicit retries and quality warnings remain real stored evidence. Only designated demo organizations are seeded; no provider jobs or upload credentials are created.
